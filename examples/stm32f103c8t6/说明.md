### 3.3 方式三：工程自带的 CMake 流程

工程是用 CubeMX 的「CMake」工具链生成的，所以官方流程是：


> **本机实测：这条路走不通**，与工程本身无关，是环境组合问题：
> 1. CMake 配置阶段在 **汇编器（ASM）识别** 时 `cmake.exe` 崩溃（退出码 `0xC0000409`，CMake 3.30.5 与 4.0.3 都一样）；
> 2. `cmake` 使用 **Ninja 生成器** 时连最简单的 C 工程也崩溃，换 `-G "Unix Makefiles"` 则正常（但 ASM 那步仍崩）。
>
> 因此本工程提供了 §3.1 的直接编译脚本作为主力方案。若你换到一台 CMake 正常的电脑，CMake 流程只需 §3.4 的第 1 处修改就能工作。

### 3.4 为适配 GCC 5.2.1 做的两处修改（重要）

**① `cmake/gcc-arm-none-eabi.cmake`：补上 `-mthumb`**

```diff
-set(TARGET_FLAGS "-mcpu=cortex-m3 ")
+set(TARGET_FLAGS "-mcpu=cortex-m3 -mthumb ")
```

原因：Cortex-M3 是**纯 Thumb 内核**。本机这套 GCC 默认按 ARM 模式编译，会直接报错：

```
error: target CPU does not support ARM mode
```

**② `STM32F103XX_FLASH.ld`：删除 `(READONLY)` 段属性**

```diff
-  .ARM.extab (READONLY) : /* ... remove it if using GCC10 or earlier. */
+  .ARM.extab : /* (READONLY) removed: only supported by GCC11+/binutils 2.38+ ... */
```

共 5 处（`.ARM.extab` / `.ARM` / `.preinit_array` / `.init_array` / `.fini_array`）。
原因：`(READONLY)` 需要 **GCC 11+ / binutils 2.38+**，本机是 GCC 5.2.1 / binutils 2.25.90，链接报错：

```
STM32F103XX_FLASH.ld:105: non constant or forward reference address expression for section .ARM.extab
```

链接脚本自己的注释也写了「GCC10 或更早就删掉它」。删掉后对 GCC 11+ 同样合法，所以这个改动是安全的。

> ⚠️ 如果以后用 CubeMX 重新生成代码，这两处会被覆盖回去，需要重新改（或换成 GCC 11+ 的工具链，那第 ① 处仍需保留 `-mthumb`，第 ② 处可保留原样）。

## 4. 烧录到单片机（ST-Link + OpenOCD）

### 4.1 接线

| ST-Link | 单片机 | 说明 |
|---|---|---|
| SWDIO | **PA13** | 数据 |
| SWCLK | **PA14** | 时钟 |
| GND | GND | **必须共地** |
| 3.3V | 3V3 | **必须接**！OpenOCD 靠这根线检测目标电压，不接会直接报 0 V 拒绝连接 |

也可以不用 ST-Link 供电、板子插自己的 USB 供电，但 **3.3V 这根线仍然要接**（当电压检测用）。

**ST-Link V2 克隆的 10 脚（2×5）排针有两个变种，引脚定义不同，且丝印经常标错**，详见 [stlink-clone-adapter](https://github.com/noahp/stlink-clone-adapter)。两个变种的 3.3V **都在第 7、8 脚**：

| | 变种 1（较老） | 变种 2（较新） |
|---|---|---|
| 1 / 2 | RST / **SWDIO** | RST / **SWCLK** |
| 3 / 4 | **GND** / GND | SWIM / **SWDIO** |
| 5 / 6 | SWIM / **SWCLK** | **GND** / GND |
| 7 / 8 | **3.3V** / 3.3V | **3.3V** / 3.3V |
| 9 / 10 | 5.0V / 5.0V | 5.0V / 5.0V |

判定自己手上是哪个变种：拔掉 ST-Link，用万用表通断档量——
**3、4 脚互通 = 变种 1**；**5、6 脚互通 = 变种 2**（那一对就是 GND）。
然后用万用表确认第 7/8 脚对 GND 是 3.3 V，再按变种把 SWDIO/SWCLK 接到 PA13/PA14。

> 单片机一般用板子上的 4 针 SWD 排针（丝印 3V3 / SWDIO / SWCLK / GND），或直接飞线到 PA13(第 34 脚)、PA14(第 37 脚)、3V3、GND。

### 4.4 验证真的烧进去了（不需要 LED）

固件本体是 CubeMX 骨架，**没有点灯的代码，肉眼看不到现象**，所以用 OpenOCD 回读芯片内容验证：

```powershell
& $OCD -s $SD -f interface/stlink.cfg -f target/stm32f1x.cfg `
       -c "init" -c "halt" -c "mdw 0x08000000 4" -c "resume" -c "shutdown"
```

期望输出里前两个字应该是：

| 地址 | 期望值 | 含义 |
|---|---|---|
| `0x08000000` | `20005000` | 初始 MSP = 0x20000000 + 0x5000（20 KB SRAM 顶部） |
| `0x08000004` | `0800xxxx`（**奇数**） | Reset_Handler 地址，Thumb 地址最低位为 1 |

校验和也可以对比：`program ... verify` 输出的 `** Verified OK **` 就说明 Flash 内容与 elf 完全一致。

### 4.5 报 `Target voltage: 0.000000` 时怎么查

这是本机遇到过的真实故障，OpenOCD 会这样拒绝连接：

```
Info : STLINK V2J46S7 (API v2) VID:PID 0483:3748
Info : Target voltage: 0.000000
Error: target voltage may be too low for reliable debugging
Error: init mode failed (unable to connect to the target)
```

含义很明确：**ST-Link 的电压检测脚（TVCC / 3.3V）上量到 0 V**。按可能性从高到低排查：

**⓪ 同时插了多个 ST-Link（本机最终就是这个原因）**
电脑上插了 2 个 ST-Link 时，OpenOCD **只会打开其中一个**，如果打开的刚好是没接板子的那个，读到的就是 0.000000 V，看起来像「板子没接」。
拔掉多余的 ST-Link，只留接板子的那一个；或者用序列号指定：

```powershell
& $OCD -s $SD -f interface/stlink.cfg -c "adapter serial <序列号>" -f target/stm32f1x.cfg -c "init; targets; shutdown"
```

序列号可以从设备管理器看，或者先跑一次 `-Probe` 看它打开的是哪台。**实测：拔掉多余的那个之后，同一套接线立刻读出 `Target voltage: 3.333601` 并成功烧录。**

**① 克隆的「变种」判断错了**
克隆排针有变种 1 / 变种 2 两套**完全不同**的引脚定义，而外壳和丝印经常按另一套标注（见 §4.1 的出处）。若按错的变种接 GND，就等于**没有共地**，OpenOCD 的 ADC 会读到 0.000 V 并直接拒绝连接。

两种接法的完整对照（3.3V 都在第 7/8 脚）：

| 接到单片机 | 变种 1 接法 | 变种 2 接法 |
|---|---|---|
| PA13 (SWDIO) | **pin 2** | **pin 4** |
| PA14 (SWCLK) | **pin 6** | **pin 2** |
| GND | **pin 3 或 4** | **pin 5 或 6** |
| 3V3 | **pin 7 或 8** | **pin 7 或 8** |

判定方法（30 秒）：拔下 ST-Link，用万用表**通断档**量——`3–4 脚互通 ⇒ 变种 1`，`5–6 脚互通 ⇒ 变种 2`（互相导通的那一对才是 GND）。
没有万用表就**直接按变种 1 重接一次再试**：只是挪 3 根线，最坏结果是白试一次。

**② 3.3V 根本没接** —— ST-Link 的 3.3V **必须**连到板子 3V3，即使板子自己插 USB 供电也要接，它同时是电压检测线。

**③ 板子确实没电 / 3V3 是 0 V** —— 拔掉 ST-Link，只给板子插 USB，量板子 3V3 对 GND 应为 3.3 V。

**④ 排线、杜邦线接触不良** —— 换线，或直接焊到测试点。

**⑤ SWDIO/SWCLK 接反** —— 电压已读到 3.3 V 但仍 `init mode failed` 时，把这两根对调再试。

**⑥ PA13/PA14 被程序占用** —— 本工程没有占用（`gpio.c` 未配置任何引脚），可排除。

**⑦ 电压正常仍连不上** → 加 `-Erase`（可能被读保护），或降低速度：在 cfg 后加 `-c "adapter speed 480"`。

> 本机实测全过程：ST-Link 是 `V2J46S7`（丝印 `SWDIO=pin4 / SWCLK=pin2 / GND=pin6 / 3.3V=pin8`，即变种 2 标法），一开始 OpenOCD 三种驱动（`stlink.cfg`、`stlink-hla.cfg`、`stlink-v2.cfg`）读到的目标电压**始终是 0.000000**，接线反复确认无误仍不通过（OpenOCD **没有**任何忽略电压的开关，`hla_ignore_target_voltage` 命令不存在）。
> 最后发现根因是 **⓪：电脑上同时插了两个 ST-Link**，OpenOCD 打开的恰好是没接板子那一个。拔掉多余的 ST-Link 后，同一套接线立刻读出 `Target voltage: 3.333601`，烧录一次成功。

## 5. 上电后芯片在做什么

`main()` 的流程：`HAL_Init` → `SystemClock_Config`（HSI 8 MHz，无 PLL）→ 初始化 GPIO/USART1/USART2/USART3 →
`osKernelInitialize` → `MX_FREERTOS_Init`（创建 `defaultTask` 和 `appTask`）→ `osKernelStart`。

- `defaultTask`：空循环 `osDelay(1)`，没有业务逻辑；
- `appTask`：**联网协议包主任务**——驱动 ESP8266 连 WiFi → 连 broker → 走 MQTT 3.1.1 握手 → 周期上报数据，
  全部过程和结果通过**串口1(PA9) 打印日志**（`printf` 重定向到 USART1）；
- 板上没有用户 LED，所以「串口1 有没有输出」就是判断程序是否跑起来的唯一现象。

> 早期版本里这个任务是 `debugTask`（心跳 + 串口2↔串口1 原始双向透传）。现在原始双向透传已**降级为备用调试方案**，
> 由 `APP_BRIDGE_DEBUG_ENABLE` 宏控制（见 §5.3），默认关闭，串口1 只做日志输出。

### 5.2 备用调试方案：串口2(ESP8266) ↔ 串口1 原始双向透传

> **默认关闭**。打开方式：把 `Core/Inc/app_config.h` 里的 `APP_BRIDGE_DEBUG_ENABLE` 改成 `1` → `build.cmd` → `flash.cmd`。
> 打开后 `appTask` 不启动，改由本节这段「原始串口透传」任务运行，用来在协议栈出问题时**绕过软件直接看模块原始字节**。
> 关闭时（`= 0`）本节全部代码被 `#if` 裁掉，不占 Flash / RAM。

**做什么**：

- **方向 A（ESP8266 → 电脑）**：USART2(PA2/PA3) 用 **DMA1_Channel6 循环模式**接收，任务每 2 ms 检查一次 DMA 写指针，
  把"这段时间新到的"那段数据**原样转发**到串口1(PA9)。串口1 上就能实时看到串口2 收到的一切。
- **方向 B（电脑 → ESP8266）**：USART1(PA9/PA10) 用 **DMA1_Channel5 循环模式**接收，同样按写指针差取新数据，
  **原样转发**到串口2 TX(PA2)。于是在串口助手里直接敲 `AT` 就能发给 ESP8266，实现双向透传。

**接线**：

| ESP8266 | 单片机 | 说明 |
|---|---|---|
| TX | **PA3** | ESP 发 → STM32 收（进 DMA） |
| RX | **PA2** | STM32 发 → ESP 收 |
| RST / EN | **PA8** | 复位/使能（低电平=复位，实测 PA8=0 时一个字节都不来） |
| VCC / GND | 3V3 / GND | |

**代码位置**（全部在 CubeMX 的 `USER CODE` 区，重新生成代码不会丢）：

| 文件 | 位置 | 内容 |
|---|---|---|
| `Core/Inc/usart.h` | `USER CODE BEGIN Includes` | `extern DMA_HandleTypeDef hdma_usart2_rx;` / `hdma_usart1_rx;` |
| `Core/Src/usart.c` | `USER CODE BEGIN 0` | 两个 DMA 句柄定义（DMA1_Channel6 / DMA1_Channel5） |
| `Core/Src/usart.c` | `USER CODE BEGIN USART1_MspInit 1` | DMA1_Channel5 循环模式配置 + `__HAL_LINKDMA`（电脑→ESP 方向） |
| `Core/Src/usart.c` | `USER CODE BEGIN USART2_MspInit 1` | DMA1_Channel6 循环模式配置 + `__HAL_LINKDMA`（ESP→电脑 方向） |
| `Core/Src/freertos.c` | `USER CODE BEGIN Init` | `APP_BRIDGE_DEBUG_ENABLE=1` 时：两次 `HAL_UART_Receive_DMA()` 启动两个方向的接收（调度器起来之前就启动，不丢开头数据）；`=0` 时改为 `esp_at_init()` |
| `Core/Src/freertos.c` | `USER CODE BEGIN Application`（`#if APP_BRIDGE_DEBUG_ENABLE` 内） | `BridgePump()` / `BridgeWriteUart()` + 主循环里的两个方向写指针差转发 |

**原理（为什么用「指针差」而不用回调）**：
循环模式下 DMA 永远不停；`CNDTR` 从 512 递减到 0 再自动重装，所以
`pos = 512 - CNDTR` 就是 DMA 当前的写指针（0..511）。任务每 2 ms 读一次，
`[lastPos, pos)` 之间的就是这段时间新到的数据；若 `pos < lastPos` 说明回绕了，分两段取。
**这样不需要任何中断，也不需要反复重启 DMA**（回调方式每次都要重启，数据一密就丢）。
两个方向各有一份 512 B 缓冲和各自的写指针（`rx2DmaBuffer`/`rx2LastPos`、`rx1DmaBuffer`/`rx1LastPos`），
由同一个 `BridgePump()` 复用这段逻辑。

启动时还做了两件事：关掉两个 DMA 通道的 TC/HT/TE 中断和两个串口的错误中断（EIE），
因为本项目靠轮询取数据，中断没人处理反而会留下悬空标志。
（注意 `HAL_UART_Receive_DMA()` 内部本身会打开 DMA 的 TC/HT 中断并把串口 `CR3.EIE` 置 1，所以必须显式清掉。）

> 注意：串口1 现在被 DMA1_Channel5 循环接收占用（`huart1.RxState` 一直是 BUSY），
> 所以 `main.c` 里给 `scanf()` 用的 `__io_getchar()`（走 `HAL_UART_Receive(&huart1,…)`）会直接返回 `HAL_BUSY`。
> 本工程没有任何地方调用它，所以无影响；以后要用串口1 收命令行，请从 `rx1DmaBuffer` 里取数据。

**注意**：轮询周期必须小于「缓冲被写满一圈」的时间。512 B @115200 ≈ 44 ms，
所以 `BRIDGE_POLL_MS = 2` 有 20 倍余量；若把串口2 波特率提到 921600 以上，
要相应加大 `BRIDGE_RX_BUFFER_SIZE` 或减小 `BRIDGE_POLL_MS`。

**可配置项**（都在 `Core/Inc/app_config.h` 第 4 节）：

| 宏 | 默认 | 说明 |
|---|---|---|
| `APP_BRIDGE_DEBUG_ENABLE` | 0 | 总开关：**1 = 才编译并运行本节的透传调试方案**，0 = 正常运行 `app_net` 联网任务 |
| `BRIDGE_RX_BUFFER_SIZE` | 512 | DMA 循环缓冲大小（字节），两个方向共用 |
| `BRIDGE_POLL_MS` | 2 | 转发任务轮询周期（ms） |
| `BRIDGE_OUTPUT_HEX` | 0 | 改成 1 = 把 串口2 → 串口1 的数据转成十六进制打印（看二进制协议用）；电脑发给 ESP 的指令始终原样透传 |
| `BRIDGE_TO_ESP_ENABLE` | 1 | 双向透传开关：1 = 电脑发的字节转给 ESP8266；0 = 退回单向（串口2 → 串口1） |
| `BRIDGE_REPORT_PERIOD_MS` | 1000 | 心跳，改成 **0** 关闭——串口1 上就只剩串口2 的数据 |

> 早先用于验证接线的 `DEBUG_ECHO_ENABLE`（轮询回显）**已删除**：串口1 现在由 DMA1_Channel5 循环接收，
> 再调 `HAL_UART_Receive(&huart1,…)` 只会返回 `HAL_BUSY`，两者不能共存。

> 之前 PA8 是浮空输入，实测此时 `usart2_rx=0 B`（ESP 完全不工作），必须用调试器把它拉高才行，

#### 5.3.2 为什么手写 MQTT，而不是用 AT 的 MQTT 命令

本机 ESP8266 的 AT 固件是 **v1.2.0.0（2016-07-01 / SDK 1.5.4.1）**，**没有** `AT+MQTTUSERCFG` / `AT+MQTTCONN`
（这些要 AT ≥ v1.7.0 才有）。所以这里直接进**透传模式**，在 TCP 字节流上手写 MQTT 3.1.1 报文：

```
固定头 = 1 B (报文类型<<4 | 标志) + 1~4 B 变长「剩余长度」
变量头 = 例如 CONNECT 的协议名/协议级别/连接标志/keepalive
载荷   = client_id / 主题名 / 消息体
```

好处是**不挑固件版本**，任何能透传的模块都能跑；坏处是要自己把报文拼对（本项目全部放在 `mqtt_client.c`）。

#### 5.3.3 两种链路模式（宏切换）

#### 5.3.5 断线识别 + 自动重连（透传模式下也能识别服务器断开）

**问题**：透传模式（`AT+CIPMODE=1`）下串口上跑的是 TCP 裸字节流，一旦对端关掉连接，
软件如果只看"有没有收到数据"是**发现不了**的，会一直以为在线。

**第一步：怎么发现"断了"（两条并行，谁先命中就重连）**

| # | 检测手段 | 位置 | 说明 |
|---|---|---|---|
| ① | 逐字节匹配 `"CLOSED"` | `esp8266_at.c` 的 `esp_at_drain()` | 透传下对端关 TCP 时模块会吐 `CLOSED` 并自动退出透传。用**逐字节状态机**匹配，`CLOSED` 被拆到多次 `read` 里也不会漏（之前的实现在单次 read 内找串，会漏） |
| ② | keepalive 超时 | `app_net.c` 的 `net_online_loop()` | 定期发 PINGREQ，等不到 PINGRESP 就判定链路已死（服务器进程被 kill、TCP 半开时靠这条兜底） |

检测接口：`esp_at_link_closed()` / `esp_at_clear_link_closed()`。

**第二步：怎么"精确恢复"（顺序很关键）**

```
检测到断线
   │
   ├─ ① exit transparent (+++)      ← 必须先退出透传，否则后面发 AT 没人理
   │
   ├─ ② AT 探活？──不应答──▶ PA8 硬复位(拉低 300ms) ──▶ 再探活
   │        │应答
   │        ▼
   ├─ ③ AT+CWJAP? 诊断 WiFi 到底断没断
   │      ├─ 还连着 AP  →  只重开 TCP      （快，约 2 s）
   │      └─ 没连 AP    →  CWJAP 重连 WiFi （慢，约 10 s）
   │
   └─ ④ CIPCLOSE → CIPMUX=0 → CIPSTART → 进透传 → MQTT CONNECT/SUBSCRIBE
```

四个必须讲清楚的坑：

1. **必须先 `+++` 退出透传，再发 AT**。透传模式下串口上跑的就是 TCP 字节流，
   这时候发 `AT` 只会被当成 TCP 数据丢出去，模块根本不解释——所以"断线后直接发 AT 探活"
   是没意义的。代码里这一步在 `net_esp_recover()` 的最前面，日志里能看到
   `[esp] exit transparent (+++)`。
2. **用 `AT+CWJAP?` 判断 WiFi，而不是 `AT+CIPSTATUS`**。后者的 `STATUS:<n>` 数字含义
   在不同 AT 固件版本里不一样；而 `AT+CWJAP?` 连上时回 `+CWJAP:"ssid",...`、没连回 `No AP`，
   无歧义。若老固件不支持该查询（回 ERROR），会**安全退化成"重连 WiFi"**这条慢路，不会出错。
3. **`AT+CIPCLOSE` 必须排在 `AT+CIPMUX` 前面**。模块里还挂着半开的旧 link 时，
   `AT+CIPMUX` 会回 `link is builded` + `ERROR`，让这次重连直接失败、白等一个重试周期。
4. **`"CLOSED"` 只在透传模式下才当断线信号**（`esp_at_watch_byte()` 开头的
   `if (s_transparent == 0U) return;`）。AT 指令模式下 `"CLOSED"` 是**正常应答文本**：
   重连时 `AT+CIPCLOSE` 关掉旧 link 就会回一行 `CLOSED`。不加这个判断会踩到
   **无限 `+++` 循环**：`CIPCLOSE` 的 `CLOSED` 被误判成"对端断了" → `s_closedFlag=1`
   → 刚建好链进 `net_online_loop()` 第一件事就是 `tcp closed by peer -> reconnect` 立刻返回
   → 下一轮 `net_esp_recover()` 又看到"还在透传" → 再 `+++`……如此往复，日志上就是
   `ONLINE` 与 `[esp] exit transparent (+++)` 交替刷屏。实测日志里 `CIPSTART` 失败后
   尾随的 `CLO` / `CLOS` / `CLOSE` 半截文本，正是这个字节流在 AT 模式下漏进来的证据。
   同理，`net_mqtt_start()` 失败时也要先 `esp_at_exit_transparent()` 再返回，
   免得把"透传中"的状态留给下一轮。

**实测 A：手动停掉 EMQX（`emqx.cmd stop`）再启回来**（2026-10-07，见 §8）

```
[net] keepalive timeout -> reconnect        # 服务器进程没了，TCP 半开 → 靠 keepalive 兜底
[esp] exit transparent (+++)                # ← 整段掉线期只出现 1 次，之后不再刷 +++
> AT                → OK       [net] ESP8266 alive
> AT+CWJAP?         → +CWJAP:"yzf",...       # WiFi 还在
[net] wifi still up -> reopen TCP only
> AT+CIPCLOSE       → CLOSED                # ← 就是这行 "CLOSED"，修好前会在这里被误判成断线
> AT+CIPMUX=0       → OK
> AT+CIPSTART="TCP","192.168.137.1",1883  → ERROR   # broker 停了，端口关闭
[net] esp_at_cmd(...) -> err 2 / link up failed, retry in 5000 ms
        ⋮  （每 5 s 一轮：AT → CWJAP? → CIPCLOSE(ERROR) → CIPMUX → CIPSTART(ERROR)，
        ⋮    干净地静默重试，全程不再出现 "+++"）
*** 启动 EMQX ***
> AT+CIPSTART → CONNECT → CIPMODE=1 → 进透传
[net] mqtt CONNACK ok / mqtt subscribed
[net] ============== ONLINE ==============   # 自动恢复，seq 继续累加
```

**实测 B：用相同 `client_id` 抢占，把设备从 broker 上踢掉**

```
[kick] CONNACK = 20020000                   # 另一路客户端用同 client_id 连上，broker 踢掉设备
[net] keepalive timeout -> reconnect
[esp] exit transparent (+++)                # 仍然只有 1 次
```

两种断法都是**一次重试即恢复**，无需硬复位；只有模块真卡死（AT 完全不应答）时才动用 PA8 硬复位。
掉线期间重连是**静默的**（只有每轮一条 `link up failed`），不会刷 `+++`。

> 代价是心跳变频繁、功耗略增。若对端是**正常关闭**（发 FIN），走 `CLOSED` 这条路几乎立刻就能发现。

#### 5.3.6 下行命令：往订阅主题发一句话就能改 MCU 里的变量

**目标**：订阅到某个主题 → 按名字把某个变量改掉，不用为每个变量单独写解析函数。

**用法（三步）**

1. 声明一个 `int32_t` 变量；
2. 在 `app_net_task()` 跑起来之前登记它：

```c
static int32_t s_ledState;

app_net_init();
app_net_var_register("led", &s_ledState);   /* 之后发 "led=1" 就会把它改成 1 */
```

3. 往 `APP_MQTT_TOPIC_SUB`（默认 `stm32/down`）发文本即可：

```bash
# 用 mosquitto_pub / MQTTX 等任意 MQTT 客户端发到 stm32/down 主题
mosquitto_pub -h 192.168.137.1 -t stm32/down -m "led=1"
mosquitto_pub -h 192.168.137.1 -t stm32/down -m "period=5"          # 一次改一个
mosquitto_pub -h 192.168.137.1 -t stm32/down -m "led=0;period=10"   # 一次改多个
```

**报文格式**：`名字=数值`，多条用 `;` `,` 空格或换行分隔。
数值支持十进制与 `0x` 十六进制，可带 `+` / `-`。例：`led=0x1`、`offset=-3`。

**日志**：

```
[net] down stm32/down = period=3
[net] cmd: period = 3
```

名字没登记 → `[net] cmd: unknown var xxx`；数值非法 → `[net] cmd: bad value for xxx`。

**你自己加一个可改变量的完整动作**：加变量 + 加一行 `app_net_var_register()`，
需要的话再把 `APP_NET_VAR_MAX` 调大。不用碰解析代码。

> 实现落点：`mqtt_client` 提供 `mqtt_set_publish_callback()`（收到 PUBLISH 回调），
> `app_net.c` 的 `net_on_publish()` 负责认主题 + 解析 + 改表。
> 回调在 `app_net` 任务上下文同步执行，和主循环同线程，**不需要加锁**；
> 回调参数指向接收缓冲，用完即弃，不能存指针。

#### 5.3.7 移植到别的工程要改什么

1. 把 `app_config.h` / `esp8266_at.[ch]` / `mqtt_client.[ch]` / `app_net.[ch]` 五个文件拷过去，加入编译；
2. 改 `app_config.h` 里的 WiFi / broker / 主题（**这一步是必须的**）；
3. 提供两个串口对象：`esp_at_init()` 里绑定的 ESP 串口（本工程 USART2）和日志串口（本工程 USART1）；
4. 保证 ESP 的 EN/RST 脚能复位（本工程 PA8，上电拉低 300 ms 再拉高）；
5. 在 RTOS 里起一个任务调 `app_net_task(NULL)`（或裸机主循环里周期调 `app_net_poll()`）。

> **在 3 KB 堆下跑任务**：`configTOTAL_HEAP_SIZE` 只有 3072 B，`appTask` 用
> `StaticTask_t` + `StackType_t[]` + `osThreadAttr_t` 填 `cb_mem`/`stack_mem` **静态分配**，完全不占 FreeRTOS 堆。
> 自己加任务时也要这么做。

## 6. 常见问题（FAQ）

| 现象 | 原因 / 解决 |
|---|---|
| `无法加载文件 build.ps1，因为在此系统上禁止运行脚本` | PowerShell 执行策略。用 `build.cmd`，或加 `-ExecutionPolicy Bypass` |
| `.ps1` 报一堆 `Unexpected token` / 中文乱码 | 脚本没存成 **UTF-8 with BOM**。用「另存为 → UTF-8 带 BOM」重存 |
| `error: target CPU does not support ARM mode` | 缺 `-mthumb`（见 §3.4 ①） |
| `non constant or forward reference address expression for section .ARM.extab` | 链接脚本 `(READONLY)` 与老 binutils 不兼容（见 §3.4 ②） |
| `undefined reference to '_exit'` | 链接时缺 `--specs=nano.specs`，或没把 `Core/Src/syscalls.c` 加进源文件列表 |
| `Target voltage: 0.000000` | **先确认只插了一个 ST-Link**（插两个时 OpenOCD 可能打开没接板子那个）；其余见 §4.5 |
| 接线明明没错，电压却一直是 0 V | 同上：多个 ST-Link 抢设备，或克隆丝印标错（§4.5 ⓪①） |
| `Error: init mode failed` 但电压正常 | SWDIO/SWCLK 接反、速度太高、或芯片被读保护（加 `-Erase`） |
| OpenOCD 报找不到 cfg | 少了 `-s <scripts 目录>`，或 `-f interface/stlink.cfg` 路径写错 |
| `cmake --preset Debug` 直接崩 | 见 §3.3，用 `build.cmd` 绕过 |
| 串口助手收不到任何数据 | ① 接线：TTL 的 **RX 要接 PA9**（不是 PA10，收发要交叉）；② **GND 必须共地**；③ 串口助手确认 115200-8-N-1；④ 引脚是否真的在 PA9/PA10——用 §5.1 的寄存器自检表确认 `AFIO_MAPR` bit2=0、`GPIOA_CRH`=0x...4B4 |
| 串口收到乱码 | 波特率不匹配（确认 115200），或没共地 |
| 串口助手提示「拒绝访问 / 端口被占用」 | 该 COM 口已被别的软件（或另一个串口助手窗口）打开，只能有一个程序占用 |
| 串口1 上收到的是乱码，最后又有明文 | 串口2 上接的是 ESP8266：**启动日志是 74880 波特率**（在 115200 下就是乱码），之后 AT 固件才切到 115200。见 §5.2 |
| 串口2 收不到任何数据 | 确认设备真的在发；ESP8266 要先把 **PA8 拉低再拉高**复位才会吐启动信息（PA8=0 时实测 0 B/s） |
| 在串口助手里发 `AT` 给 ESP8266 没应答 | 前提是本节方案已启用（`APP_BRIDGE_DEBUG_ENABLE = 1`）。① 串口助手要**打开回显**才能看到自己发的字符；② ESP8266 的 **RX 必须接 PA2**（不是 PA3）；③ 确认 `BRIDGE_TO_ESP_ENABLE = 1`；④ ESP 的 AT 固件默认 115200，被改过就试 74880/9600；⑤ 把 `BRIDGE_REPORT_PERIOD_MS` 设回 1000，看心跳行里的接收计数有没有增长，可判断「电脑发的字节到底有没有进来」 |
| 联网日志停在 `wifi join failed` | ESP 回 `+CWJAP:n`：**1=连接超时，2=密码错误，3=找不到该 AP，4=连接失败**。最常见的 **3** 是热点没开，或热点开在 **5 GHz**（ESP8266 只支持 2.4 GHz） |
| `[net] ESP8266 not responding` | 模块没上电/没复位。确认 PA8 上电后被拉低 300 ms 再拉高（§2），以及 USART2 的 PA2/PA3 交叉接对。若是**重连时**出现，固件会自动跟进 `-> hardware reset (PA8)` 兜底（§5.3.5） |
| 断线后日志出现 `hardware reset (PA8)` | 正常兜底动作：对端断开后模块卡在透传里 AT 不应答，固件用 PA8 复位模块再重连。若频繁出现且每次都能恢复则无需处理；若复位后仍 `still dead`，检查 PA8 接线与模块供电 |
| 发到 `stm32/down` 的命令没反应 | ① 确认订阅成功（日志有 `mqtt subscribed: stm32/down`）；② 主题名与 `APP_MQTT_TOPIC_SUB` 完全一致；③ 变量名要先 `app_net_var_register()` 登记过，否则日志会打 `unknown var`；④ 载荷格式必须是 `名字=数值` |
| `mqtt CONNECT failed, status 1` | `1 = MQTT_ERR_PARAM`：`mqtt_client_t` 还没绑定传输层。检查任务里有没有先调 `app_net_init()`（本 bug 已修复，见 §8 实测记录） |
| `mqtt CONNECT failed, status 5` | `5 = MQTT_ERR_REFUSED`：broker 拒绝了连接。常见原因是 broker 开了鉴权而 `APP_MQTT_USERNAME/PASSWORD` 留空，或 client_id 与别的在线客户端重复 |
| 一直 `keepalive timeout -> reconnect` | broker 没回 PINGRESP：① 确认 `APP_MQTT_BROKER_HOST/PORT` 和 EMQX 监听端口一致（1883）；② 电脑防火墙是否放行 1883；③ ESP 和 broker 是否在同一网段（对比日志里的 STAIP 和 broker IP） |
| 上不了网但 WiFi 连上了 | 检查 Windows 移动热点是否开启：本机热点网卡应是 `192.168.137.1`；若本机 IPv4 只有 `192.168.x.x` 别的网段，说明热点没开，ESP 连的可能是另一个同名 SSID |
